**Method**

The research-backed way to do a PhD-level subsystem-by-subsystem walkthrough is:

1. Start with `concerns -> viewpoints -> views`, not files. ISO/IEC/IEEE 42010 says architecture descriptions should be organized around stakeholder concerns, viewpoints, views, and correspondences, so the unit of explanation is a subsystem view, not a directory dump.
2. Recover the `as-built` architecture before explaining it. SEI’s architecture reconstruction work treats subsystem recovery as successive abstraction over source and artifacts, not guesswork from names alone.
3. Use at least two evidence channels: `static structure` and `dynamic behavior`. Cornelissen’s dynamic-analysis work shows static dependencies alone are insufficient; runtime traces materially improve comprehension.
4. Anchor the walkthrough in `features/scenarios`. Eisenbarth et al. show the reliable way to understand large systems is to tie features to executed components, then use dependency analysis to narrow to self-contained components.
5. For each subsystem, produce the same packet: `purpose`, `source-of-truth files`, `interfaces`, `persistent state`, `runtime role`, and `failure/transition risks`. That is the “Views and Beyond” move: document the view plus the beyond-view information.

5. Compare the gate’s decision to that human ground truth.

Why this matters: if humans see the gate verdict first, they get biased. A blind review is a cleaner test of whether the gate really matches human judgment.

**Simple example**

- the task description
- the screenshot after the run

- `gate_passed`
- `gate_score`
- gate deficiencies

- Rater A says: `overall_passed = true`
- Rater B says: `overall_passed = true`

That becomes `multi_rater_consensus`.

If the gate also said `true`, that is an agreement.

If the gate said `false`, that is a disagreement and likely a gate false negative.
